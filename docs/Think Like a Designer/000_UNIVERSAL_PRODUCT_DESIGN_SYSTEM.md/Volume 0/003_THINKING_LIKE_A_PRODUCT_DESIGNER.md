# Purpose

This document teaches how to think before designing.

Learning CSS, Figma, Bootstrap or Tailwind is easy.

Learning how to make good design decisions is difficult.

This document develops that mindset.

---

# Stop Thinking Like A Developer

A developer often thinks

"I need a card."

A product designer thinks

"Why does this information need to become a card?"

Huge difference.

---

# The Product Design Mindset

Every screen answers four questions.

Who is the user?

↓

What is the goal?

↓

What information is required?

↓

What is the simplest path?

Everything else comes afterwards.

---

# Users Don't Visit Pages

Users don't think

"I'm opening Dashboard."

They think

"I need to check today's deliveries."

They don't think

"I'll open Projects."

They think

"I need to find Project A."

Design around goals.

Never pages.

---

# Every Pixel Pays Rent

Imagine every pixel costs money.

Would you keep it?

Every

border

shadow

gradient

animation

icon

button

must justify its existence.

If it cannot,

remove it.

---

# Components Are Conversations

A button is asking

"Would you like to continue?"

An error message is saying

"Something went wrong."

A card is saying

"This information belongs together."

Every component communicates.

---

# Start With Questions

Before opening Figma or VS Code ask

Who is using this?

Why?

Where?

How often?

Under what conditions?

What happens if they fail?

What happens if the network disappears?

What happens on mobile?

What happens with one hand?

What happens at night?

What happens outdoors?

---

# Every Feature Has States

Never design

"The screen."

Design

Loading

Skeleton

Ready

Empty

Success

Error

Offline

Refreshing

Deleting

Disabled

Archived

Searching

Filtering

Sorting

Most products spend more time in these states than in their ideal state.

---

# Information Before Decoration

Users should understand

before

they admire.

Understanding always comes first.

---

# The Five Questions

Every feature should answer

Can users discover it?

↓

Can users understand it?

↓

Can users use it?

↓

Can users recover from mistakes?

↓

Can users remember it?

If any answer is no,

redesign it.

---

# Good Design Removes Decisions

Every unnecessary decision creates friction.

Good interfaces reduce thinking.

Examples

Auto-format phone numbers.

Auto-save drafts.

Remember previous selections.

Predict common actions.

Use sensible defaults.

Guide instead of asking.

---

# Design Is Editing

The first version usually contains too much.

Professional designers remove.

Remove buttons.

Remove words.

Remove colors.

Remove borders.

Remove animations.

Until removing anything else would reduce clarity.

---

# Build For The Future

Never ask

"Will we need this?"

Ask

"If we need this later,

can the system support it?"

Scalability begins before implementation.

---

# Think In Systems

Don't design

One modal.

Design

Every modal.

Don't design

One table.

Design

Every table.

Every new component should strengthen the design system.

---

# Every Component Is Reusable

Ask

Can this be used elsewhere?

Can another project use it?

Can mobile reuse the same concept?

Can AI understand this?

Can another developer understand it six months from now?

---

# Think Beyond The Happy Path

Professional designers spend enormous time designing

Edge Cases.

Examples

No internet.

Slow internet.

No results.

Permission denied.

Expired session.

Missing image.

Video unavailable.

Corrupt file.

GPS unavailable.

Payment failed.

Driver cancelled.

Construction project delayed.

Design for reality.

---

# Learn From Reality

Observe

Construction workers.

Drivers.

Laboratory technicians.

Customers.

Managers.

Accountants.

Watch how they work.

Real behavior teaches better design than trends.

---

# Good Design Is Invisible

The best compliment is not

"Beautiful UI."

The best compliment is

"It was easy."

---

# The Product Designer's Checklist

Before approving any feature ask

□ Does this solve a real problem?

□ Is there a simpler solution?

□ Does it reuse existing patterns?

□ Does it support every state?

□ Does it work without images?

□ Does it work without JavaScript?

□ Does it work with a keyboard?

□ Does it work on mobile?

□ Does it work offline where applicable?

□ Can AI build this consistently?

Only then is the design ready.

# Final Thought

Software changes.

Frameworks change.

Languages change.

Design trends change.

People do not.

Learn people,

and your designs will remain valuable for decades.
